All code read end-to-end (every route, lib, component, the migration, config). Here's the audit.

## Architecture overview

Next.js 14 App Router app where a Vercel cron (`/api/cron/daily-mock`, 22:00 UTC) generates 5 JLPT N2 questions per day via Gemini 2.5 Flash with a 4-attempt verify/retry state machine, stores them in Supabase (`n2_questions` + `n2_mocks` keyed by JST date), then fans out notification emails via Gmail SMTP. Students sign in (password or Google OAuth), take the mock in a client-side stepper (`/today`), POST answers to `/api/attempts`, and view results, streaks, per-subtype progress, and a twice-weekly shared "revision digest." Server Components do most data access through a cookie-session Supabase client; a service-role client is used in crons and — notably — in some user-facing read paths. It's a Jackson-only Phase-1 product, but several things below will bite even a single user daily.

## Top issues (ranked by impact)

1. **Unsubscribe token verification is 100% broken** — `lib/email.ts:208` — `signUnsubscribeToken` produces `base64url(userId.ts).sig` = **2** dot-separated parts (base64url has no dots), but `verifyUnsubscribeToken` requires `parts.length === 4` and then destructures a 3-part format that the signer never produces. Every unsubscribe link in every email fails with "invalid or expired." That's a CAN-SPAM violation surface and guarantees spam reports. — Fix: sign and verify the same format, e.g. `b64(userId).ts.sig` (3 parts) with `payload = ${b64UserId}.${ts}`.
2. **`/api/dev-signup` is an open, unauthenticated admin endpoint** — `app/api/dev-signup/route.ts:14-30` — anyone can create unlimited auto-confirmed accounts (`email_confirm: true`) with *any email address they don't own*, via the service-role key, no rate limit. It's wired into the live `/auth` signup flow (`app/auth/page.tsx:79`). — Fix: gate it behind a shared secret or delete it and turn on Supabase's normal signup with confirmation.
3. **Date off-by-one in emails and result masthead** — `lib/email.ts:99` and `app/result/[date]/page.tsx:100-105` — `new Date(\`${date}T00:00:00+09:00\`)` is 15:00 UTC of the *previous* day, then `.getUTCDate()`/`.getUTCMonth()` read UTC. Every daily email says "July 22" on the July 23 mock; the result-page masthead shows the wrong day always and the wrong month near month boundaries. — Fix: format with `toLocaleDateString('en-US', { timeZone: 'Asia/Tokyo' })` for day/month/year, as the month in `email.ts:98` already correctly does.
4. **Attempt correctness is client-supplied and unvalidated** — `app/api/attempts/route.ts:70,97-99` — the server stores `correct` from the client's `correct_map` and accepts arbitrary `question_id`s not checked against the date's mock (the validated `date` field is then never used — `challenge_id` is null). Streaks, `/progress` stats, and the cross-user revision digest (`app/api/cron/revision-digest/route.ts:66-79`) are all poisonable, and an accidental client bug silently corrupts data. Bonus contradiction: with `correct_map` absent, `buildRow` (`route.ts:46`) records `false`, not `null` as the comment claims — legit answers get marked wrong. — Fix: fetch `n2_mocks[date].question_ids` + `n2_questions.correct_answer` server-side, reject unknown ids, compute `correct` server-side.
5. **Submit failure is completely silent** — `app/today/interactive-mock.tsx:252-267` — `fetch` result: only `res.ok` sets `submitted`; a non-OK response shows nothing, and a thrown fetch (offline, timeout) escapes the `try/finally` (no `catch`) as an unhandled rejection. User finishes 5 questions, taps 提出する, button flickers back to normal, answers lost, no message, streak broken. — Fix: add a `catch` + visible error state with a retry.
6. **Landing page uses UTC date while everything else uses JST** — `app/page.tsx:35` — between 00:00–09:00 JST the signed-in landing looks up *yesterday's* mock, finds it, and shows "Begin today's mock →"; clicking through to `/today` (JST-based, `app/today/page.tsx:72`) says the mock doesn't exist yet. Also skews the "Issue N" ordinal. — Fix: use the same `sv-SE`/`Asia/Tokyo` helper used everywhere else.
7. **The project is not under version control** — `~/projects/japanese-n2` is not a git repo (only one migration file exists; migrations 001–008 referenced in comments are gone). No rollback, no history, no schema source of truth — you cannot audit what RLS policies actually exist on `n2_attempts`/`n2_questions`/`n2_mocks` from the codebase. — Fix: `git init`, commit, and dump the live schema (`supabase db pull`) into `supabase/migrations/`.
8. **Email fan-out shares the cron's 60s budget after publish** — `app/api/cron/daily-mock/route.ts:598-677` — sequential sends with up to 3 retries + 3s backoff per subscriber, started after up to 48s of generation. A timeout mid-fanout means some subscribers silently get no email and no `n2_email_send_log` rows, and the run can't be retried (idempotency guard at line 291 skips the day). — Fix: move fan-out to its own cron/route keyed off "mock published, email not yet logged."

## Frontend audit

- **Bug**: `app/today/interactive-mock.tsx:176-178` — the correct/wrong answer reveal is keyed to `submitting` (true only during the POST), not `submitted`. The reveal flashes for the duration of the network roundtrip, then *reverts to neutral* once submission succeeds. Almost certainly meant to be `submitting || submitted`.
- **Bug**: `app/today/page.tsx:86-93` — a Supabase *error* (network, RLS, etc.) renders the same `NoMockToday` state as a genuinely missing mock. DB outages will be reported to the user as "今日のモックはまだありません."
- **Bug**: `app/result/[date]/page.tsx:264-271` — `NoAttemptYet` copy says 「下のボタンから受験してください」 but renders no button.
- **Issue**: `app/today/interactive-mock.tsx:111-114` — the header date uses the browser's local clock (`new Date()`), while line 134 renders `mock.date` (JST). A user outside JST sees two different dates a few pixels apart.
- **Issue**: no way to navigate back to earlier questions before submitting (`interactive-mock.tsx` only ever does `setIndex(index + 1)`), and answers are lost on accidental reload — everything lives in component state. For an exam app, one mis-tap of × 閉じる (which has no confirm) discards the whole session.
- **Issue**: `app/today/page.tsx:107` ships `correct_answer`, `explanation`, and per-option `note` for all 5 questions to the browser before the user answers anything — the day's answer key is one devtools tab away. Same via the anon PostgREST API if `n2_questions` has anon SELECT (which the public `/revision` page implies).
- **Perf**: `app/layout.tsx:94-97` — `getSession()` is awaited in the root layout and the result is never used (nothing is passed to `children`). That's an extra per-request Supabase roundtrip on every page, on top of each page's own `getSession()` and the middleware's — three session touches per request. Likely a big chunk of the observed 3592ms server latency noted at `layout.tsx:110`.
- **Perf**: `middleware.ts:47-49` — matcher runs the session-refresh middleware on `/api/cron/*`, `/api/unsubscribe`, and all public assets except three hardcoded paths. Exclude `/api/cron` and static files.
- **A11y**: `app/globals.css` has zero `prefers-reduced-motion` handling while the core layout is a permanently rotated card (`transform: rotate(8deg)`, globals.css:401); the answer options are independent buttons with `aria-pressed` (`components/OptionButton.tsx:73`) rather than a `radiogroup`, so screen readers hear no "1 of 4" context; the 90-day activity calendar cells (`app/progress/page.tsx:155-163`) expose data via `title` only, which is invisible to keyboard and touch users.

## Backend audit

- **Bug**: `app/api/subscribe/route.ts:50-58` — the opt-*out* branch upserts `subscribed_at: now` alongside `unsubscribed_at: now`, clobbering the original subscription date despite the comment "keep subscribed_at for audit."
- **Bug**: `app/api/unsubscribe/route.ts:38-44` — the upsert result is unchecked, and for a user with no existing row it violates `email NOT NULL` (`migrations/2026-07-21-email-feature.sql:15`) — the route then renders "Unsubscribed." even though the write failed. (Currently unreachable because of Top issue #1, but it will surface the moment that's fixed.)
- **Bug**: `n2_subscribers.email_send_count` is never incremented anywhere (fan-out at `daily-mock/route.ts:667-672` only sets `last_sent_at`), so the Settings "Emails sent" row (`app/settings/page.tsx:122-127`) can never appear.
- **Bug**: `app/api/cron/daily-mock/route.ts:589-596` — the rotation-state update's error is not checked. If it fails after publish, the next day re-plans the *same* cycle day and the LRU rotation silently stalls on repeated subtypes.
- **Issue**: `lib/get-result.ts:90-100` — a user-facing read path uses the **service-role key** with a hand-built REST URL to dodge a claimed supabase-js chain bug. This bypasses RLS where it should apply, and the "bug" is very plausibly a missing/broken RLS SELECT policy on `n2_attempts` being masked (note `/progress` reads the same table fine with the session client at `app/progress/page.tsx:41-47`). Also, a mock row with empty `question_ids` produces `question_id=in.()` → PostgREST 400 → user-facing 500.
- **Issue**: `daily-mock/route.ts:308-317` — 10 sequential awaited recency queries burn ~1-2s of a 48s budget that the route itself documents as tight; trivial `Promise.all`.
- **Issue**: `app/api/cron/daily-mock/route.ts:283` — if `CRON_SECRET` is unset in an environment, the check compares against the literal string `"Bearer undefined"`, which an attacker can just send. Fail closed when the env var is missing (same in `revision-digest/route.ts:32`).
- **Issue**: `app/api/cron/revision-digest/route.ts:52-59` — the window starts at the *previous digest's run_date* 00:00 JST, so attempts made the morning of the last digest day are double-counted in the next one.
- **Issue**: `lib/streak.ts:26` — `limit(500)` caps the walk at ~100 days (5 attempts/day; fewer with duplicate submissions). Around the 100-day mark — which is the whole point of a streak app with a Jul 2027 target — the streak silently stops growing. Select distinct dates or raise/paginate.
- **Dead code**: `lib/types/attempts.ts`, `lib/types/result.ts`, `lib/types/auth.ts` (~500 lines) have zero importers; `total_ms` is computed and discarded at `app/api/attempts/route.ts:85-86`.

## Security & data integrity

- `/api/dev-signup` (Top issue #2) is the headline: unauthenticated account creation with arbitrary pre-confirmed emails = pre-hijack of any email address plus a free `auth.users` spam vector.
- Client-authoritative correctness + unvalidated question ids (Top issue #4) means every derived stat — streaks, accuracy, and the *cross-user* revision digest — trusts the browser.
- `GET /api/unsubscribe` mutates state on GET. Once the token bug is fixed, mail-client link scanners (Gmail, corporate proxies) will auto-unsubscribe users by prefetching the link. Use the confirmation-page-then-POST pattern or support `List-Unsubscribe-Post` one-click (the email currently sets no `List-Unsubscribe` header at all — `lib/email.ts:246-255` — which also hurts deliverability).
- `UNSUBSCRIBE_SECRET` falls back to a hardcoded string `'dev-only-secret-rotate-this-in-v1'` (`lib/email.ts:33-34`) — if the env var is ever missing in prod, tokens become forgeable by anyone reading this file. Throw instead of defaulting.
- Service-role key used where user-scoped clients should suffice: `lib/get-result.ts:91`, `app/settings/page.tsx:37`. Each extra service-role path is one more place a refactor can accidentally leak cross-user data.
- RLS policies for `n2_attempts`, `n2_questions`, `n2_mocks`, `n2_revision_digests`, `n2_rotation_state`, `n2_pipeline_runs` are **not in the repo** — unauditable from code. Given `/revision` reads via anon-capable client, the entire question bank (with answers) is presumably anon-readable via PostgREST with the public anon key.
- No rate limiting on any POST endpoint (`/api/attempts`, `/api/subscribe`, `/api/dev-signup`).

## Bigger redesigns worth considering

- **Server-authoritative attempts.** Make `/api/attempts` the single source of truth: validate ids against the date's mock, compute correctness server-side, enforce one submission per user per mock (unique index on `(user_id, question_id)` or a real per-mock attempt row), and stop shipping `correct_answer` to the client pre-submit — return the graded breakdown from the POST instead. This one change fixes issues #4, the devtools answer leak, duplicate-submission dedup hacks in three places (`get-result.ts:117-126`, `progress/page.tsx:56-62`, the `submittingRef`), and makes the revision digest trustworthy.
- **Split email fan-out out of the generation cron.** A `mock published && no send-log row` reconciliation cron is idempotent, retryable, and immune to the 60s budget. While there, move sends to a proper provider with delivery webhooks — Gmail app-password SMTP from a serverless function is the first thing that will break at any scale.
- **Consolidate session handling.** One `getSession()` per request (middleware refreshes, pages read), one date helper module (`jstToday()` exists in four copies with two bases), and retire the raw-REST service-role workaround in `get-result.ts` after actually diagnosing the RLS/chain issue it papers over.
- **The mock-taking flow as a real exam surface**: back-navigation before submit, sessionStorage persistence against reloads, a confirm on exit, and radiogroup semantics. For an app whose entire job is "do 5 questions every single day for a year," the cost of one lost session is a broken streak — the thing the product is built around.

The generation pipeline itself (`daily-mock` v2 retry machine) is genuinely well-constructed — fail-closed, traced, idempotent. The weak layer is everything between the database and the user: date handling, the attempts contract, and the email path.
